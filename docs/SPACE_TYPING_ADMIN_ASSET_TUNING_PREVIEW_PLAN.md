## 1. Product decision

The target Admin experience is **not** “upload an arbitrary file and hope the game renders it correctly”.

The target is an administrator-facing **Asset Tuning Studio**:

```text
Select / Upload compatible asset
        ↓
Validate against the canonical slot profile
        ↓
Tune only production-consumed settings
        ↓
Preview through child-owned production presentation modules
        ↓
Test supported states
        ↓
Save Draft
        ↓
Validate
        ↓
Review Changes
        ↓
Publish
```

The asset is source material. The owning gameplay/presentation domain decides how that exact immutable asset version is used.

### Hard rule — no fake settings

> A control must not appear merely because a renderer function accepts a number or because Portal can draw an input. A writable control requires a canonical persisted domain field and a production runtime consumer.

Examples of values that **do not automatically become authorable fields** merely because runtime code uses them:

- draw-time `x` / `y`;
- `scale` parameters supplied by a caller;
- aim angle;
- recoil state;
- engine boost;
- roll / pitch / yaw generated by gameplay;
- animation time;
- VFX intensity constants.

These may be useful **preview scenario inputs** while remaining non-authorable.

---

## 2. Goals

1. Let administrators choose or upload compatible assets without source-code/path editing.
2. Pin exact immutable `assetVersionId` values when a published domain definition references Media V2.
3. Expose only settings actually consumed by the production child runtime.
4. Use the same child-owned renderer/presentation/effect modules for Admin preview and gameplay.
5. Preview Idle / Move / Fire / Skill / Hit / Low HP / Death only where the current runtime genuinely supports those scenarios.
6. Keep preview visually dominant and controls simple.
7. Keep Media, domain configuration, revisions, CAS, permissions and audit ownership separate.
8. Reuse UI primitives and slot-profile concepts without creating a giant universal Ship/Skill/Projectile/Shop schema.
9. Make unsaved preview completely non-mutating.
10. Fail closed when a requested capability is not canonical yet.

---

## 3. Non-goals

The first implementation is not Blender, After Effects, a VFX graph editor or a generic game-engine editor.

Out of scope until the production child runtime explicitly supports them:

- arbitrary rig creation/repair;
- arbitrary GLB compatibility;
- arbitrary GLB animation generation;
- skeletal animation authoring;
- shader graph editing;
- node-based VFX authoring;
- frame-by-frame sprite authoring;
- arbitrary filesystem paths;
- free-form JSON for normal administrators;
- Portal-side reimplementation of gameplay rendering;
- a shadow Shop product model;
- a synthetic Weapon domain created only to satisfy UI design.

## 4. Current runtime reality — source of truth for A5.0

The following findings are locked from the code audit at the reviewed child checkpoint. Workers must re-audit if child HEAD moves.

### 4.1 Current Ship 2D path

Production Ship presentation currently includes:

- `src/characters/renderer.ts`
- `src/characters/visuals.ts`
- `src/characters/ship-motion.ts`
- `src/vfx/ship-exhaust.ts`
- `src/vfx/player-shots.ts`

The current illustrated Ship path uses a shared Ship sprite sheet with a hard-coded per-character sprite index, with procedural fallback rendering.

`drawCharacterShip()` accepts runtime draw inputs such as position, scale, aim, recoil and boost. Those arguments are not automatically persisted Ship presentation settings.

### 4.2 Existing Ship Admin visual policy has an authority gap

Current Admin/runtime policy exposes Ship `visual` overrides including silhouette/colors/wingSpan/bodyLength/engineCount.

However, the audited production renderer path still obtains its profile from the bundled `characterVisualProfile()` source. Therefore A5.0 must prove and, if necessary, repair the authority chain before treating these fields as production-backed authoring.

Required chain:

```text
Admin persisted field
→ child runtime policy materialization
→ canonical Ship presentation resolver
→ production renderer
→ Admin Preview Harness using the same resolver
```

A field is not `SUPPORTED NOW` merely because validation accepts it.

### 4.3 Current projectile path

Player projectile identity and visual behavior are currently code-owned through:

- `src/characters/projectiles.ts`
- `src/vfx/player-shots.ts`

Recipes include production concepts such as speed, bend, trail style, muzzle positions, painted FX family and impact presentation. These are current runtime definitions, not automatically Admin-authorable fields.

### 4.4 Current VFX path

The current VFX Admin contract is explicitly runtime-derived/read-only.

Production VFX includes procedural systems such as:

- `src/vfx/skill-fx.ts`
- `src/vfx/ship-exhaust.ts`
- `src/vfx/player-shots.ts`
- combat/boss effects in the production game path.

Therefore A5 must not turn arbitrary uploaded images into fake VFX definitions.

### 4.5 Current SFX path

SFX is mixed:

- sampled local audio;
- semantic sound variants;
- synthesized WebAudio voices;
- production mix/runtime logic.

A generic `sfxAssetVersionId` is not automatically a correct model for every sound binding.

### 4.6 Current production 3D path

The canonical current 3D Ship path is **not arbitrary GLB**.

Production uses a generated relief bundle loaded by:

- `src/duel/ship3d.ts`
- `src/duel/relief-model.ts`

Current bundle shape is effectively:

```text
/assets/space-typing/ships/3d/<ship>/
  model.json
  color.webp
  emissive.webp
  height.bin
```

The loader builds Three.js geometry/materials from this strict representation.

Current production does not establish a canonical arbitrary GLB + skeletal animation + semantic clip pipeline.

Therefore:

- existing generated relief bundles may be previewed;
- arbitrary GLB assignment is **DEFERRED**;
- animated GLB assignment is **DEFERRED**;
- semantic Idle/Attack/Cast/Hit/Death clip mapping is **DEFERRED** until a production animation runtime exists.

### 4.7 Current preview helpers are not visual production preview

Existing `*-registry-preview` helpers validate/materialize policy data. They are useful but they are **not** the Asset Tuning Studio visual renderer.

Use distinct concepts:

```text
Policy/Data Preview
≠
Production Visual Preview Harness
```

Do not build a Portal canvas on top of registry-preview output and call that production preview.

## 6. Architecture boundary — Media vs domain tuning

### Media V2 owns

- logical asset identity;
- immutable asset versions;
- bytes/reference components;
- media kind;
- provenance;
- metadata;
- usage references;
- archive/version lifecycle.

### Domain definitions own

Only after a canonical production consumer exists:

- exact assigned `assetVersionId`;
- supported scale/offset/rotation correction;
- domain presentation presets;
- projectile/effect/SFX references;
- animation mapping where production supports it;
- preview scenario defaults where appropriate.

### Invariants

1. Media must not own Ship/Skill/Projectile transform tuning.
2. Published definitions pin exact immutable `assetVersionId`; never silently follow `currentVersionId`/`latest`.
3. Upload/version creation remains `changesGameplay: false`.
4. Gameplay changes only when a published domain revision references a Media version.
5. Rollback must continue resolving the exact historical version.
6. Portal must never convert `assetVersionId` into an arbitrary filesystem/source path for gameplay.

## 7. Asset Slot Profile — reusable capability metadata, not universal gameplay schema

Asset Slot Profile is retained, but its responsibility is tightened.

Conceptually:

```ts
type AssetSlotProfile = {
  slotId: string;
  domain: string;
  label: string;
  writable: boolean;
  readonlyReason?: string;
  canonicalField?: string;
  consumerRevision: string;
  allowedMediaKinds: string[];
  allowedComponentRoles?: string[];
  allowedFormats?: string[];
  requirements: {
    alpha?: "required" | "allowed" | "forbidden";
    aspectRatio?: { min: number; max: number };
    minWidth?: number;
    minHeight?: number;
    maxBytes?: number;
  };
  supportedControls: SupportedPresentationControls;
  previewStates: string[];
  processingProfileId?: string;
};
```

### Hard invariant

> Asset Slot Profile is capability metadata. It must never become the persisted universal Ship/Skill/Projectile/Shop definition.

Each domain retains its own schema and validator.

The Portal must not independently maintain capability truth. Profiles must originate from child-owned/jointly audited contracts tied to a production consumer revision.

## 8. Capability-driven controls

A writable control requires all of the following:

```text
persisted domain field
canonical validator
runtime materializer/resolver
production consumer
preview consumer using the same path
defined apply boundary
```

Missing any item → the field is not writable.

Conceptual control metadata may include:

```ts
type SupportedPresentationControls = {
  uniformScale?: { min: number; max: number; step: number };
  offsetX?: { min: number; max: number; step: number; unit: "px" | "world" };
  offsetY?: { min: number; max: number; step: number; unit: "px" | "world" };
  rotation?: { min: number; max: number; step: number; unit: "deg" | "rad" };
  idleMotionPreset?: readonly string[];
  recoilPreset?: readonly string[];
  effectScale?: { min: number; max: number; step: number };
};
```

This structure describes real capabilities; it must not create them.

## 9. Media import, validation and derived assets

Safe target flow:

```text
RAW SOURCE
   ↓
Media V2 upload/reference admission
   ↓
Slot compatibility validation
   ↓
Optional non-destructive processor
   ↓
New immutable derived version/components
   ↓
Exact assetVersionId
   ↓
Domain definition
   ↓
Production preview
```

### 9.1 Current decision for derived variants

Current Media V2 does not yet model enough explicit derived-version lineage for A5 to silently create processed runtime variants.

Therefore the first A5 slice should prefer **validation-only processing**.

If derived variants are required, Media architecture must first add explicit immutable lineage such as:

```text
sourceAssetVersionId
processorId
processorVersion
processingProfileId
derivedAt
```

and a clear provenance/storage rule for derived blobs.

Never overwrite source bytes.

### 9.2 2D validation

Safe early capabilities include:

- dimensions;
- aspect ratio;
- alpha-channel policy;
- file-size budget;
- safe-area/transparent-bound warnings.

Automatic trim/crop is forbidden unless the slot profile defines a deterministic compatible processor.

### 9.3 3D validation

The first 3D profile must match the real production relief bundle.

Do not validate future GLB rules inside the current relief profile. A future GLB profile must be a separate capability with its own loader, resource budget and animation semantics.

## 10. Production asset resolver gate

Before per-entity Media assignment is writable, child production needs a canonical resolver seam:

```text
Domain definition
  exact assetVersionId
        ↓
Production media/component resolver
        ↓
Validated runtime component or bundle
        ↓
Production renderer/loader
```

The same resolver must be usable by the Preview Harness.

### Requirements

- exact immutable version resolution;
- typed component roles;
- no raw administrator path input;
- fail closed on wrong/missing components;
- no implicit switch to current/latest Media version;
- cache immutable resources by version ID where safe;
- resolve Admin-owned blobs and runtime-reference bundles through explicit trusted rules.

Until this exists, Asset Picker may select versions for Media management but a Ship field must not pretend the game consumes them.

## 11. Preview architecture — child-owned production parity

### 11.1 Forbidden

```text
Portal-only fake renderer
Portal-only movement formula
Portal-only VFX approximation presented as canonical
copied child renderer code inside Portal
hard-coded preview animation presented as gameplay behavior
full Test Lab state mutation used as normal Admin editing
```

### 11.2 Preferred boundary

```text
Portal Asset Tuning Studio
        ↓
versioned preview protocol
        ↓
Child Admin Visual Preview Harness
        ↓
production asset resolver
production Ship/projectile renderer
production motion/state modules
production VFX/SFX bindings where safe
production 3D renderer where supported
```

For the current separate parent/child architecture, a child-owned preview route/frame is preferred over importing game code into Portal.

Direct shared-module import is acceptable later only if the build architecture genuinely shares the same production modules and does not create a second renderer.

### 11.3 Existing registry previews remain separate

Keep clear names/concepts:

```text
PolicyPreview / RegistryPreview
= validation + materialization + data inspection

VisualPreviewHarness
= actual production presentation
```

### 11.4 Preview protocol

A conceptual envelope:

```ts
type AdminVisualPreviewRequest<TCandidate> = {
  protocolVersion: 1;
  previewSessionId: string;
  requestId: number;
  entityType: "ship" | "projectile" | "skill" | "shop-presentation";
  entityId: string;
  candidate: TCandidate;
  scenarioId: string;
};
```

Candidate payloads are domain-specific validated types. No arbitrary JSON execution semantics, paths, scripts or source URLs.

Recommended commands/events:

```text
READY
LOAD_CANDIDATE
SET_TUNING
SET_SCENARIO
PLAY
PAUSE
RESET
DISPOSE
STATE
WARNING
ERROR
```

### 11.5 Same-origin iframe/postMessage requirements

If iframe hosting is used:

- exact `event.origin` validation;
- exact `event.source === iframe.contentWindow` validation;
- protocol handshake before commands;
- preview-session nonce/ID;
- monotonic request IDs;
- ignore stale async loads/results;
- strict schema validation;
- no PlayerSave writes;
- no ShopInstance persistence;
- no active revision mutation;
- no Media `currentVersionId` mutation;
- explicit `PAUSE`/`DISPOSE` lifecycle;
- teardown all listeners on route change;
- pause expensive rendering when hidden;
- structured errors/warnings returned to Portal.

`sandbox="allow-scripts allow-same-origin"` must not be treated as the primary security boundary. Controlled route + origin/source/schema validation are authoritative.

### 11.6 Draft vs Published

Preview may switch:

```text
Draft | Published
```

Both must be real definitions rendered through the same child harness.

Unsaved Draft candidate is ephemeral and never replaces `ACTIVE_*_RUNTIME_SESSION` singletons or active persisted config.

## 12. Preview lifecycle and performance

Admin preview is more demanding than long-lived gameplay because administrators repeatedly replace assets and mount/unmount scenes.

Every preview host must own and release:

- `requestAnimationFrame` loops;
- timers;
- DOM/window/document listeners;
- fetch `AbortController`s;
- stale async requests;
- Object URLs;
- audio playback/nodes/contexts owned by the preview;
- WebGL renderer/context resources;
- geometries;
- materials;
- textures;
- generated environment/PMREM textures;
- message subscriptions/channels.

### 12.1 No model reload for cheap tuning

Separate state into:

```text
Resource identity
  assetVersionId / bundle version

Cheap presentation tuning
  supported scale / offset / correction

Scenario state
  Idle / Move / Fire / Hit / ...
```

Changing a numeric transform must not reload the model if resource identity is unchanged.

High-frequency tuning should be coalesced to animation frames or safely debounced. Saving must always persist the final value.

### 12.2 Current 3D cleanup gap

The current production 3D path must be audited for Admin-specific teardown beyond renderer disposal because repeated Admin model switching can expose GPU leaks that normal gameplay does not.

A5 acceptance requires repeated mount/switch/unmount stress testing.

## 15. Projectile, Weapon, VFX and SFX boundaries

### 15.1 Projectile

Do not bury every projectile setting under Ship if the runtime is migrated to reusable projectile definitions.

However current projectile recipes are code-owned. A5.0 must decide whether to create a canonical authored Projectile domain or keep them read-only for the initial slice.

- exact visual asset/preset;
- supported size/orientation;
- trail effect reference;
- impact effect reference;
- impact SFX semantic binding;

Preview may safely support production scenarios such as Fire once / Loop / Hit / Miss before authoring exists.

### 15.2 Weapon

Current Admin/runtime architecture does not prove a first-class writable Weapon domain.

Therefore:

> A5 must not invent a Weapon entity solely because the target UI lists one.

The first Fire preview uses the current production Ship/projectile path.

Create first-class Weapon authoring only if the latest child audit demonstrates reusable runtime ownership that benefits from its own canonical definition.

### 15.3 VFX

Current contract is read-only.

A5 may preview existing effects but must not expose generic effect replacement/tuning until a canonical writable effect/preset contract is consumed by production.

Procedural effects stay procedural definitions, not Media images.

### 15.4 SFX

Do not assume every sound is an uploaded audio asset.

A future authorable binding model must distinguish at least:

```text
sample-backed Media sound
vs
runtime synthesized/semantic sound preset
```

and preserve production mixing behavior.

## 17. Revision, permission, audit and mutation safety

A5 reuses A0.5; it does not create a second revision system.

### Unsaved tuning

```text
local ephemeral candidate
→ preview only
→ no persistent mutation
```

### Save Draft

```text
whole-config immutable draft revision
→ validated canonical fields/references
→ active runtime unchanged
```

### Publish

Use existing expected-active-revision CAS semantics.

The UI must not imply “Publish Ship” means only Ship changed when the revision contains other changes. `Review Changes` must show the real whole-config change scope.

### Upload

Media upload/version/archive alone remains non-gameplay mutation.

### Permissions and audit

All new mutations must use existing actor/permission/audit foundations. Do not create bypass endpoints for preview convenience.

If runtime variants are required, extend Media lineage/provenance before generating them.

### A5.0.7 — Build Child Admin Visual Preview Harness

Use production presentation modules. Do not copy renderer logic.

Start with one representative Ship and current production assets.

### A5.0.8 — Build domain candidate adapter

Allow ephemeral candidate injection into the harness without mutating active runtime singletons/persistence.

### A5.0.9 — Harden lifecycle/security

Implement origin/source/protocol/request validation, stale cancellation, pause/dispose and GPU/audio cleanup.

### A5.0.10 — Draft/Published sources

Both definitions must render through the same harness.

### A5.0 exit gate

A5.1 may start only when:

- no proposed writable field lacks a production consumer;
- one real field has end-to-end production consumption or the first slice is intentionally preview-only;
- production preview parity is proven;
- preview is non-mutating;
- lifecycle cleanup is tested;
- branch/source-of-truth reconciliation is documented.

## 21. Automated verification requirements

### Runtime consumer parity

For each writable field, test:

```text
published domain field
→ runtime materialization
→ canonical resolver
→ production presentation input
```

A validator/registry preview test alone is insufficient.

### Exact Media pinning

Required scenario:

```text
publish entity referencing assetVersion A
create newer version B / make B current in Media Library
fresh gameplay still resolves A
```

### Upload-is-not-gameplay

Verify Media upload/version/archive does not change:

- active revision;
- production domain definition;
- PlayerSave;
- ShopInstance.

### Preview parity

Given the same resolved definition/scenario/time inputs, production gameplay and Admin harness must use the same presentation resolver/modules.

Pixel snapshots may supplement but cannot replace authority/path tests.

### Preview isolation

Full preview must not mutate:

- active revision;
- PlayerSave;
- persisted ShopInstance;
- published definitions;
- Media current version pointers.

### 3D compatibility

Until GLB migration exists, tests must reject unsupported arbitrary GLB as a Ship production model.

Strict relief bundles must fail closed on missing/invalid required components.

### postMessage/security

Test:

- wrong origin;
- wrong source window;
- unsupported protocol;
- malformed candidate;
- stale request ID;
- arbitrary path/URL/script attempts;
- commands before handshake.

### Lifecycle

Repeated mount/switch/unmount must prove:

- no orphan RAF;
- no listener growth;
- stale fetches cancelled/ignored;
- Object URLs revoked;
- audio stopped;
- WebGL resources released.

### CAS

If active revision changes while an editor is open, publish must conflict cleanly with no partial media/domain mutation.

### VFX guard

Unknown/non-authorable VFX fields continue to fail closed. Never weaken validators to make Studio inputs pass.

## 22. Manual acceptance requirements

### UX

On common laptop/desktop sizes:

- preview remains visually dominant;
- no nested-scroll/card maze;
- no parameter wall;
- normal Admin does not see raw source paths, child SHA, protocol details or manifests;
- Advanced remains optional.

### Keyboard/accessibility

Administrator can complete the core flow with keyboard:

```text
choose compatible asset
→ choose exact version
→ change a scalar via numeric input
→ change preview scenario
→ Save Draft
→ Review Changes
```

Requirements:

- no drag-only operation;
- every slider has numeric equivalent;
- visible focus;
- tooltip/help usable without hover;
- focus restored after pickers/dialogs;
- status/error not conveyed by color only;
- play/pause/state changes have textual/ARIA status.

### Production visual comparison

Manually compare representative production gameplay and Admin preview for:

- hull presentation;
- motion pose;
- muzzle origin;
- projectile identity;
- trail/impact identity and timing;
- relevant SFX/effect identity.

### 3D stress

Repeatedly switch preview entities/resources, hide/show the tab and navigate away/back. Verify no runaway GPU/CPU/audio behavior.

## 23. Anti-clutter gate

The page fails if:

- preview becomes a small card next to a large settings wall;
- more than roughly 5–7 unrelated primary controls appear in one group;
- preview requires opening a separate page after every edit;
- Basic requires knowledge of manifests/anchors/protocols;
- permanent helper paragraphs replace tooltips/help;
- disabled unsupported controls are displayed just to look feature-rich;
- raw IDs/paths dominate labels;
- every runtime constant becomes a slider;
- seven scenario buttons are always shown even when most are irrelevant.

The page passes when an administrator can immediately answer:

1. **What asset/effect am I editing?**
2. **What will the game actually show/do with this candidate?**
3. **Am I viewing Draft or Published?**

## 24. Final invariant

The finished Admin must feel simple because architecture absorbs complexity, not because Portal hides a second fake implementation.

Target end state:

```text
Administrator chooses a compatible exact asset version
        ↓
Admin shows only production-backed controls
        ↓
Administrator tunes the candidate
        ↓
Child production presentation modules render it immediately
        ↓
Candidate stays isolated until Save Draft
        ↓
Validation + Review Changes + CAS Publish
        ↓
Fresh gameplay consumes the exact published definition/version
```

If any step requires Portal-only rendering logic, a shadow model, an implicit latest asset, unsupported VFX fields, or a value production does not consume, stop and return to A5.0 rather than expanding the UI.
